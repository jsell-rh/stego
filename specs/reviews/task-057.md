# Review: Task 057 — Lifecycle Slot Proto Definitions and Component Registry Update

## Round 1

- [ ] **`BeforePatchRequest` missing entity name field.** All other slot request messages include entity identification: `before_create` and `before_upsert` via `CreateRequest.entity`, all four `after_*` protos via `string entity`, and `validate` via `string entity`. `BeforePatchRequest` has `patch_fields`, `existing_entity`, and `caller` — but no entity name. 7 of 9 slot request messages convey entity type; `before_patch` does not. The spec (rest-crud/spec.md line 307) says before slots "receive the parsed input and the caller's identity"; for `before_create` the parsed input (`CreateRequest`) includes entity name. The spec's stated use case for `before_patch` is "enforce field-level permissions" (line 312) — a fill implementing entity-specific permission rules cannot determine the entity type from the request alone. Add `string entity` to `BeforePatchRequest` (field number 4, or restructure to match the `after_patch` pattern: `entity`, `patch_fields`, `existing_entity`, `caller`).

- [ ] **`BeforeDeleteRequest` missing entity name field.** `AfterDeleteRequest` includes both `string entity` and `string deleted_entity_id`. `BeforeDeleteRequest` only has `string entity_id` and `caller` — no entity type name. The spec's use case (line 313) is "check dependencies, prevent deletion of active resources" — both require knowing the entity type. The asymmetry with `AfterDeleteRequest` (which does include entity name for the same data: entity ID + caller) is an inconsistency. Add `string entity` to `BeforeDeleteRequest`.
